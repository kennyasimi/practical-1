Проверено через docker ps: работают lakehouse-minio, lakehouse-pg, lakekeeper, trino; Spark запускается одноразовым контейнером (docker run --rm).

Показывает разницу между интерактивным (Trino) и batch (Spark) подходами                                                  |

### Скрипты, которыми поднимал стек

```bash
# MinIO (Silo — свободный форк, т.к. MinIO убран с Docker Hub)
docker run -d --name lakehouse-minio `
  -p 9000:9000 -p 9001:9001 `
  -e MINIO_ROOT_USER=minioadmin `
  -e MINIO_ROOT_PASSWORD=minioadmin `
  -v minio-data:/data `
  pgsty/silo:latest server /data --console-address ":9001"

# PostgreSQL — хранит метаданные Lakekeeper
docker run -d --name lakehouse-pg `
  -e POSTGRES_PASSWORD=postgres `
  -p 5432:5432 `
  -v pg-data:/var/lib/postgresql/data `
  postgres:17

# Lakekeeper — миграции БД (один раз)
docker run --rm `
  -e 'LAKEKEEPER__PG_ENCRYPTION_KEY=This-is-NOT-Secure!' `
  -e 'LAKEKEEPER__PG_DATABASE_URL_READ=postgresql://postgres:postgres@host.docker.internal:5432/postgres' `
  -e 'LAKEKEEPER__PG_DATABASE_URL_WRITE=postgresql://postgres:postgres@host.docker.internal:5432/postgres' `
  quay.io/lakekeeper/catalog:latest-main migrate

# Lakekeeper — сервер REST Catalog
docker run -d --name lakekeeper `
  -e 'LAKEKEEPER__PG_ENCRYPTION_KEY=This-is-NOT-Secure!' `
  -e 'LAKEKEEPER__PG_DATABASE_URL_READ=postgresql://postgres:postgres@host.docker.internal:5432/postgres' `
  -e 'LAKEKEEPER__PG_DATABASE_URL_WRITE=postgresql://postgres:postgres@host.docker.internal:5432/postgres' `
  -p 8181:8181 `
  quay.io/lakekeeper/catalog:latest-main serve

# Trino — SQL-движок, каталоги монтируются из папки catalog/
docker run -d --name trino `
  -p 8080:8080 `
  -v "${PWD}\catalog:/etc/trino/catalog" `
  trinodb/trino:476
```

## 4. Медальон — решения по каждому слою

Формат — PARQUET. Колоночный формат: движок читает только те колонки, которые нужны запросу, а не всю строку. Это де-факто стандарт экосистемы — его одинаково читают Trino, Spark и любой другой Iceberg-совместимый движок, поэтому данные не «привязаны» к одному инструменту. В нашем Q16 запрос читает 4 колонки из 9 у part и 2 из 5 у partsupp — колоночность даёт прямой выигрыш по I/O.

Сжатие — ZSTD. По результатам бенчмарка §5: размер практически совпадает с GZIP (2.295 МБ vs 2.238 МБ, разница ~2.5%), но запрос Q16 на ZSTD выполнился заметно быстрее (1.777 с vs 2.797 с, ~36% быстрее). ZSTD — современный компромисс «размер ↔ скорость ↔ CPU»: сжимает почти как GZIP, а декомпрессия дешевле. GZIP оправдан только для архивных, редко читаемых данных.

Изоляция по слоям. Каждый слой — отдельный warehouse в Lakekeeper и отдельный бакет в MinIO (bronze, silver, gold). Таблицы лежат в схеме q16 внутри своего каталога: bronze.q16._, silver.q16._, gold.q16.\*. Физическое разделение позволяет независимо назначать права доступа (например, аналитикам — только gold), настраивать политику хранения (Bronze — дольше, Gold — можно пересоздавать) и не смешивать «сырое» с «очищенным».

Партиционирование — нет. На sf1 таблицы маленькие (сотни КБ–единицы МБ), партиции только добавили бы файлов и метаданных без выигрыша. На sf100+ имело бы смысл партиционировать fact_partsupp по partkey (bucket) или dim_part по size — но это отдельный эксперимент, выходящий за рамки sf1.

Масштаб — sf1. Обоснование в §1 отчёта: sf1 целиком помещается в RAM ноутбука, все операции занимают секунды, а закономерности сжатия и чтения те же, что на sf10/sf100 — масштаб не меняет выводы о компромиссе кодеков.

## 5. Тесты производительности

### Методика

- **Bronze-копии для сравнения кодеков** созданы отдельно от основной медальонной таблицы: `bronze.q16.raw_partsupp_none`, `bronze.q16.raw_partsupp_snappy`, `bronze.q16.raw_partsupp_gzip`, `bronze.q16.raw_partsupp_zstd` — все из `tpch.sf1.partsupp`, формат везде **PARQUET**, кодек задаётся через `SET SESSION bronze.compression_codec` перед `CREATE TABLE ... AS SELECT`. Основная медальонная `bronze.q16.raw_partsupp` остаётся в ZSTD.
- **Время запроса** — Q16-нагрузка на Bronze: `count(DISTINCT suppkey)` по `raw_partsupp_<codec>` с подзапросом по `raw_supplier` (`comment LIKE '%Customer%Complaints%'`). Запрос выполнен дважды на каждом кодеке: 1-й прогон — «холодный», 2-й — «тёплый». Перед холодным прогоном Trino и MinIO перезапускались (`docker restart trino lakehouse-minio`) для сброса кэша метаданных и страничного кэша ОС.
- **Размер** — `sum(file_size_in_bytes)` по `$files` каждой таблицы, переведён в МБ.
- **Сырые результаты:** `bench_size.csv`, `bench_q16.csv`.

### Вывод

Из четырёх кодеков **ZSTD выигрывает по обеим метрикам скорости**: cold 1.78 с — лучший результат, warm 0.34 с — тоже лучший, при размере, практически равном GZIP (2.295 vs 2.238 МБ, +2.5%). **NONE** — ожидаемый аутсайдер: без сжатия с диска читается в 2.5 раза больше байтов (5.76 МБ), поэтому cold самый медленный (2.97 с), а warm — самый медленный среди всех (0.62 с). **GZIP** даёт минимальный размер (2.238 МБ) и лучший warm среди «тяжёлых» кодеков (0.38 с), но платит самым медленным cold (2.80 с): декомпрессия дорогая, и на холодном кэше выигрыш в размере не компенсирует стоимость CPU. **SNAPPY** — середина без ярких преимуществ: быстрый декомпрессор (warm 0.42 с), но слабое сжатие (3.26 МБ). **Итог: для Bronze медальона выбираем ZSTD** — он одновременно самый быстрый на чтение (cold и warm) и по размеру не уступает GZIP. GZIP оправдан только для архивного слоя с редким чтением, NONE — только как бенчмарк-эталон.

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос                                                                           | Твой ответ                                                                                                                                                                                                                                                                                                                                                                                                 |
| -------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)?              | Lakehouse объединяет гибкость data lake (хранение любых данных в дешёвом объектном хранилище) с удобством data warehouse (SQL, транзакции, схема). Обычная БД не масштабируется на петабайты и стоит дорого; обычный data lake без каталога превращается в «болото» без схемы и транзакций. Lakehouse (Iceberg + S3 + Trino) даёт ACID, эволюцию схемы, time travel и открытые форматы без vendor lock-in. |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | В Iceberg ALTER TABLE ... ADD COLUMN меняет только метаданные — файлы данных не переписываются. Старые строки читают NULL для новой колонки. Например: ALTER TABLE silver.q16.dim_part ADD COLUMN material varchar; — операция мгновенная, старые parquet-файлы не трогаются. При чтении Trino подставляет NULL там, где колонки нет физически.                                                            |
| Пример скрипта восстановления данных из снапшота (time travel)                   | Посмотреть список снапшотов: SELECT \* FROM silver.q16."dim*part$snapshots"; Затем восстановить: ALTER TABLE silver.q16.dim_part SET TBLPROPERTIES ('iceberg.snapshot-id' = '<snapshot_id>'); или прочитать данные на конкретный момент: SELECT * FROM silver.q16.dim_part FOR VERSION AS OF <snapshot_id>; — Iceberg хранит все версии таблицы, и можно откатиться к любой.                               |

### Вывод

Spark подключён к тому же Lakekeeper REST-каталогу, что и Trino, и читает те же Iceberg-таблицы в MinIO — без экспорта, конвертации или дублирования. SHOW TABLES IN bench.lakehouse показывает все бенчмарк-таблицы, созданные Trino; count(\*) по lineitem_parquet_gzip совпадает (6 001 215); Spark читает Iceberg-снапшоты напрямую (append, тот же snapshot_id, что у Trino); агрегат по partsupp_gzip даёт 800 000 строк и 10 000 уникальных поставщиков — ровно как в Trino и как ожидается для sf1. Это подтверждает ключевое свойство lakehouse: данные открытые, один формат (Parquet + Iceberg metadata) читается разными движками. Разница только в скорости: Trino быстрее на малых объёмах (нет «налога на старт» JVM — см. §6.2, таблица Trino vs Spark), Spark выигрывает на больших ETL-нагрузках за счёт распределённости.

## 7. Выводы

Я развернул локальный Lakehouse (MinIO + Lakekeeper + Trino), построил медальон Bronze → Silver → Gold для Q16 на sf1 и провёл бенчмарк четырёх кодеков на Bronze. ZSTD — оптимальный выбор для аналитики: размер как у GZIP (+2.5%), но cold и warm чтения самые быстрые (1.78 / 0.34 с); NONE проигрывает всем, GZIP оправдан только для архивов, SNAPPY — компромисс без ярких преимуществ. Медальон на Parquet + Iceberg даёт изоляцию слоёв, эволюцию схемы и time travel при ничтожных накладных расходах на метаданные. Trino быстрее Spark на малых объёмах (2.7/0.46 с vs 12.2/11.3 с) за счёт мгновенного старта, но Spark подтвердил открытость данных: он читает те же Iceberg-таблицы через тот же Lakekeeper без экспорта.
